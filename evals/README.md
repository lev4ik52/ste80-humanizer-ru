# Сценарии проверки

`cases.json` — 50 синтетических русскоязычных и смешанных примеров,
подготовленных специально для этого проекта. Это не клиентские документы.
`triggers.json` — 12 сценариев активации: шесть положительных и шесть отрицательных.

## Поля сценария

- `source`, `genre`, `mode`: вход и редакторская задача.
- `reference`: подготовленный допустимый вариант, не единственный правильный ответ.
- `must_include`, `must_not_include`: буквальные ограничения автоматики.
- `manual_criteria`: то, что обязательно проверяет человек.
- `bad_variant`, `expected_bad_codes`: некоторые ошибочные варианты и ожидаемые сигналы.
- `manual_only_negative`: специально показанный слепой участок эвристики.

Значения `mode` и `genre` проверяются по режимам и жанрам из SKILL.md.
Строковые поля не могут состоять только из пробелов. У отрицательного примера
нужны все три поля: `bad_variant`, `expected_bad_codes`, `manual_only_negative`.
Для ручного отрицательного примера список кодов пуст; для автоматического — непуст.
В `triggers.json` поле `activate` — логическое значение, не строка или число.
Повторяющиеся запросы запрещены. Структуру обоих наборов проверяет `validate_repo.py`.

Проверки `must_include` чувствительны к регистру; `must_not_include` — нет.
Они дополняют сравнение защищённых фрагментов и числовых инвариантов.
Синоним может быть корректным по смыслу и не пройти буквальное ограничение:
такой случай надо разбирать, а не подгонять весь текст под тест.

## Проверить целостность набора

```bash
python scripts/run_evals.py
python scripts/run_evals.py --format json
```

Режим называется `reference_fixture_self_test`, поле `model_invoked` равно `false`.
Здесь проверяются готовые примеры, НЕ результаты применения скилла моделью.
Те же 50 пар включены в unit-тесты; это повторная проверка, а не ещё 50 независимых
экспериментов. Коды выхода: 0 — все ограничения пройдены, 1 — есть провалы,
2 — неправильные входные данные.

## Проверить результаты своего агента

Отдельно дайте агенту `source` вместе с режимом/жанром и установленным скиллом.
Не передавайте ему `reference`, тестовые ограничения и чужие результаты.
Сохраните все 50 ответов в следующей структуре:

```json
{
  "metadata": {
    "model": "точная версия модели",
    "agent": "клиент и версия",
    "skill_version": "1.1.0",
    "skill_commit": "фактический SHA или идентификатор пакета",
    "run_id": "идентификатор повтора"
  },
  "outputs": {
    "ru-01": "ответ на первый пример",
    "ru-02": "ответ на второй пример"
  }
}
```

В примере сокращён список ключей: настоящий файл должен содержать ВСЕ ID из
`cases.json`, без лишних и пропущенных. Пустые ответы и неверный формат — ошибки.
Сохраните файл как `candidates-run1.json` (он игнорируется Git по умолчанию).

```bash
python scripts/run_evals.py --candidates candidates-run1.json --format json
```

Проверка не вызывает модель, не оплачивает API и не отправляет данные в сеть.
Формальные успехи остаются помеченными `manual_review_required: true`.
Для разных повторов используйте разные файлы и не заменяйте плохой ответ удачным.

Активацию проверяют отдельно в конкретном клиенте с установленным скиллом:
сопоставляют фактический выбор с `activate` из `triggers.json`. Обычный Python-runner
не проверяет выбор инструмента приложением.
